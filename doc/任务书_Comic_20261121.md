将小说转化为可玩的文字游戏，核心在于把线性的叙事文本，**解构**为结构化的游戏资产（世界观、角色、事件），再通过一套**有状态的运行时引擎**，用提示词驱动 LLM 实时生成交互叙事。完全基于 OpenAI API 和 Python 的可行路径，通常遵循“**离线解构 → 结构化存储 → 在线运行时**”的分层架构。

### 🏗️ 核心工作流：六层架构

一个清晰的参考架构是“六层模型”，它将“生成漂亮文字”与“记住真实世界”的责任分离。

| 层级 | 职责 | 关键实现 |
| :--- | :--- | :--- |
| **① 表现层** | 游戏界面（Web / CLI / TUI） | FastAPI, Rich, Gradio |
| **② 指令解析层** | 自然语言 → 结构化动作 | OpenAI Function Calling / Pydantic |
| **③ 游戏状态层** | 世界真相的唯一权威（状态机） | **独立的 JSON 状态字典**，非 LLM 记忆 |
| **④ 提示词组装层** | 动态拼装上下文 | System + 世界书 + 状态 + 记忆 + 输入 |
| **⑤ 模型接口层** | LLM 调用与结构化输出 | `openai` Python SDK, `response_format` |
| **⑥ 小说抽取层** | 离线解析小说为游戏资产 | 批量 API 调用 + 结构化抽取提示词 |

这个架构的关键在于：**游戏世界的“真实状态”（如位置、背包、NPC 关系）由 Python 字典或数据库严格管理，而不是依赖 LLM 的“记忆”**。LLM 只负责根据状态和玩家输入，生成符合世界观的叙事文本。

### 📜 阶段一：离线解构——小说资产抽取

这一步的目标是将小说文本转化为结构化的“世界书”（Worldbook）和角色卡。使用 **`response_format={"type": "json_object"}`** 或 **Function Calling** 强制 LLM 输出 JSON，是保证结构稳定的关键。

#### 核心抽取提示词：剧本/场景结构化

以下提示词（改编自开源项目）能将一章小说转换为包含角色、场景和元素的 JSON 剧本：

```python
# novel_parser.py (示意)
from openai import OpenAI
import json

client = OpenAI()

EXTRACTION_PROMPT = """
你是一个专业的剧本转写专家。你的任务是将小说的**每一个情节**都转换为剧本格式，决不遗漏。
## 输出格式 (返回 JSON)
{
  "characters": [
    {"id": "char_001", "name": "角色名", "role": "主角/配角", 
     "description": "背景", "traits": ["性格标签"],
     "relationships": [{"target": "char_002", "relation": "朋友"}]}
  ],
  "scenes": [
    {
      "scene_number": 1,
      "location": {"name": "地点", "time": "时间", "description": "环境细节"},
      "characters_present": ["char_001"],
      "elements": [
        {"type": "action", "content": "动作描述"},
        {"type": "dialogue", "speaker": "char_001", "lines": ["台词1"], "emotion": "语气"},
        {"type": "transition", "content": "转场"}
      ]
    }
  ]
}
## 核心规则
- **每一段对话 = 一个场景**；**每一次人物行动 = 一个场景**；**每一次地点转移 = 一个场景**。
- 回忆/闪回**绝不能压缩**，必须作为独立场景完整展开，并像当前时间线一样处理。
- 一章 3000 字的小说，通常应产出 **4-7 个场景**。生成后请自检：场景数是否过少？
"""

def parse_novel_chapter(chapter_text: str) -> dict:
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": EXTRACTION_PROMPT},
            {"role": "user", "content": f"请解析以下小说章节：\n\n{chapter_text}"}
        ],
        response_format={"type": "json_object"},
        temperature=0.2  # 抽取任务需要稳定性
    )
    return json.loads(response.choices[0].message.content)
```

**提示词要点**：
- **强制完整性**：通过“决不遗漏”、“每一段对话=一个场景”等强规则，对抗 LLM 的“摘要倾向”。
- **闪回处理**：明确要求将回忆作为独立场景展开，否则关键情节会被压缩成一句话。
- **自检机制**：在提示词中加入数量校验（“3000字至少4个场景”），让模型自我纠正。

#### 角色关系图谱抽取

对于长篇小说，可以增加一个独立的 **“NPC 图谱分析”** 步骤，专门维护角色关系网络：

```text
你是 NPC 图谱分析师。从本轮叙事中识别新出现的角色、团体、派系，并更新它们之间的关系。
- 关系类型使用大写下划线格式：TRUSTS / FEARS / ALLY_OF / OPPOSES / WORKS_FOR 等。
- 关系强度 strength 范围 [-1, 1]：+1 极度友好，-1 极度敌对。
- 只提取本轮叙事中**明确陈述**的新事实，不要重复记录旧关系。
```


### ⚙️ 阶段二：在线运行时——状态化叙事引擎

游戏运行时，每一回合的 LLM 调用都是一个 **“上下文组装 → LLM 生成 → 状态更新”** 的循环。

#### 运行时系统提示词：导演与声音

运行时提示词需要同时承担两个角色：**叙事者（声音）** 和 **世界管理者（编织者）**。

```text
你是这个世界的“梦境心智”。你同时扮演两个角色：
• **声音 (The Voices)**：完全以当前场景中角色的口吻说话。绝不作为作者旁白，绝不提及自己是 AI。
• **编织者 (The Weaver)**：静默地决定本回合世界的变化（新地点、新角色、关系变化）。

规则：
- 保持世界基调与角色既定特质一致。角色只知道他“可能知道”的事。
- 本回合的变化应**尽可能小**，只在必要时（如玩家移动到新地点）才设置 scene_change。
- 输出必须是一个**单一的 JSON 对象**，严格遵循给定 schema，不要输出任何其他内容。
```


#### 结构化输出与状态更新（Pydantic + OpenAI）

使用 Pydantic 定义游戏状态的 schema，并通过 OpenAI 的结构化输出确保 LLM 返回的“世界变化指令”可被可靠解析。

```python
# game_engine.py (示意)
from pydantic import BaseModel
from typing import Literal, Optional
from openai import OpenAI

class WorldChange(BaseModel):
    narration: str  # 叙事文本
    scene_change: Optional[str] = None  # 新地点
    relationship_delta: Optional[dict] = None  # {"target": "char_002", "delta": 0.2}
    game_over: bool = False

client = OpenAI()

def take_turn(player_input: str, current_state: dict, worldbook: dict) -> WorldChange:
    # 1. 组装上下文（关键：状态在 Python 侧，不在对话历史里）
    context = f"""
    【当前世界状态】{current_state}
    【相关世界书条目】{worldbook.get(current_state['location'], '')}
    【玩家行动】{player_input}
    """
    
    # 2. 调用 LLM，强制结构化输出
    response = client.beta.chat.completions.parse(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": RUNTIME_DIRECTOR_PROMPT},
            {"role": "user", "content": context}
        ],
        response_format=WorldChange,
    )
    change = response.choices[0].message.parsed
    
    # 3. 在 Python 侧应用状态变更
    if change.scene_change:
        current_state["location"] = change.scene_change
    if change.relationship_delta:
        # 更新关系图谱...
        pass
    
    return change
```

这种模式的优点是**状态与叙事解耦**。LLM 不“记得”玩家在哪里，它只是根据 Python 传入的 `current_state` 来生成叙事。状态的更新逻辑由 Python 代码显式控制，杜绝了 LLM 的“幻觉”导致的世界状态混乱。

### 🧠 长上下文管理：记忆是一种“预算”

当游戏进行多轮后，对话历史会超出上下文窗口。解决方案不是简单地截断，而是**按优先级组装一个“记忆预算”**。

#### 分层记忆组装策略

每一轮构建上下文时，按以下优先级填充 token 预算：

1. **滚动摘要（Rolling Summary）** ：对之前所有剧情的 1-3 句累积摘要，始终保持。
2. **当前场景全量**：当前所在地点、在场角色的完整信息。
3. **最近 K 轮逐字对话**：保留最近的 N 轮原始交互（例如最近 5 轮）。
4. **玩家新输入**。

```python
def build_memory_context(history, current_state, budget=6000):
    context_parts = []
    tokens_used = 0
    
    # 1. 滚动摘要（始终保留）
    context_parts.append(f"【故事至今】{current_state['rolling_summary']}")
    
    # 2. 当前场景角色卡
    present_chars = current_state.get("present_characters", [])
    context_parts.append(f"【在场角色】{[worldbook['characters'][c] for c in present_chars]}")
    
    # 3. 最近对话（从新到旧填充）
    recent_turns = []
    for turn in reversed(history[-10:]):  # 最多考虑最近10轮
        turn_tokens = count_tokens(turn)  # 估算
        if tokens_used + turn_tokens > budget:
            break
        recent_turns.insert(0, turn)
        tokens_used += turn_tokens
    
    context_parts.append(f"【最近经历】{recent_turns}")
    return "\n".join(context_parts)
```

对于超长篇小说（如数百万字），还可以在离线阶段建立**向量索引**。运行时根据玩家当前位置或行动，从原始小说文本中检索相关段落，注入上下文，实现“基于原文的检索增强叙事”。

### 🧩 可选增强：多智能体与校验层

当游戏逻辑复杂时，可以拆分为多个专职 Agent，各司其职，由 LangGraph 等状态机编排。

| Agent | 温度 | 职责 |
| :--- | :--- | :--- |
| **Story Agent** | 0.7 | 生成沉浸式叙事与场景描述 |
| **Inventory Agent** | 0.3 | 处理物品增减，校验物品交互合法性 |
| **Decision Agent** | 0.3 | 解析玩家意图，判定行动成功/失败 |
| **Memory Agent** | 0.3 | 维护历史摘要与上下文压缩 |

此外，可以引入一个独立的 **“裁判”LLM 调用**，在叙事生成后校验其是否与**世界书中的硬规则**（如“此门需要钥匙”）冲突，冲突则触发重写或修正。

### 💎 总结：最小可行实现路径

如果从零开始，建议按以下顺序构建：

1. **定义 Pydantic 状态模型**：明确你的游戏世界有哪些核心变量（位置、背包、角色关系、剧情标志）。
2. **编写离线抽取提示词**：用 `response_format={"type": "json_object"}` 将一本短篇小说（或一章）解析为 `worldbook.json`。
3. **实现最小运行时循环**：`player_input → 组装上下文（System + 状态 + 世界书 + 输入）→ LLM(结构化输出) → Python 更新状态 → 输出叙事`。
4. **加入滚动摘要**：当历史超过 N 轮时，调用一次 LLM 生成摘要，替换旧历史。
5. **迭代提示词**：根据游戏中的实际表现（角色 OOC、状态矛盾、叙事干瘪），针对性调整系统提示词中的规则和示例。

这个架构的优势在于**每一步都可观测、可调试**：如果叙事出问题，检查提示词；如果状态出错，检查 Python 逻辑；如果前后矛盾，检查记忆组装策略。LLM 和游戏逻辑的边界清晰，是长期迭代的基础。
